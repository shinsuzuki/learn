## 2. プロジェクト概要

### 2.1 背景・目的
- 例:A社(買収元)とB社(被買収元)の受発注システムを統合し、業務プロセスを一本化する
- 統合の背景(M&A、業務効率化、保守コスト削減など)を明記

### 2.2 統合の方針(スコープの前提)
以下のような統合パターンのうち、どれを採るかを最初に明確化する。これにより後続要件が大きく変わる。

| パターン | 概要 | 今回の該当有無 |
|---|---|---|
| A社システムへ片寄せ | B社データをA社(Classic ASP)へ移行し、B社システムは廃止 | ○/× |
| B社システムへ片寄せ | 逆パターン | ○/× |
| 新システムへ統合 | 両社データを新システムへ移行 | ○/× |
| 連携維持(疎結合) | 双方存続、IF連携のみ | ○/× |

> 本サンプルは「A社の既存Classic ASPシステムへB社を片寄せする」パターンを想定して以降を記述。

### 2.3 対象範囲(スコープ)
- 対象業務(例:受注管理、在庫管理、請求業務 等)
- 対象システム・サーバ・DB
- 非対象(スコープ外)を明記 ※後の揉め事防止のため重要

### 2.4 プロジェクト体制・スケジュール
- 体制図(発注者/受託者/両社の業務担当・情シス担当)
- マイルストーン(現行調査→要件定義→設計→開発→移行リハーサル→本番移行→安定化)

## 3. 現行システム調査結果(As-Is)

Classic ASP改修を伴う統合では、この章の精度がプロジェクトの成否を左右します。

### 3.1 システム構成調査
| 項目 | A社(Classic ASP) | B社 |
|---|---|---|
| 言語/フレームワーク | Classic ASP (VBScript) | (例)C#/.NET, PHP等 |
| Webサーバ | IIS バージョン | |
| DB | SQL Server バージョン等 | |
| 主要ライブラリ/COMコンポーネント | ADO, 独自COM/DLL 等 | |
| 認証方式 | セッション管理方式・Cookie仕様 | |
| 外部連携IF | 決済、他部門システム等 | |
| ホスティング環境 | オンプレ/クラウド、EOL状況 | |

### 3.2 コード資産調査(Classic ASP特有の観点)
- ソース行数・ページ数(.asp / .inc ファイル数)の棚卸し
- ハードコーディングされた接続文字列・パス・認証情報の有無
- 使用しているCOMコンポーネント・サードパーティDLLの現存/保守可否
- 文字コード(Shift-JIS等)・タイムゾーンの扱い
- SQLインジェクション等の既知脆弱性の有無(改修と合わせて是正するか判断)
- IIS・Windows Serverのサポート期限(EOL)とOS/IIS更新要否
- テストコード・自動テストの有無(通常ほぼ無いため、改修時の回帰テスト方針が必須要件になる)

### 3.3 データ資産調査
- DBスキーマ一覧、テーブル数、レコード件数
- マスタデータの重複・コード体系の相違(顧客コード、商品コード等)
- データ品質(欠損、重複、不整合)の事前調査結果

## 5. 機能要件

### 5.1 業務要件一覧(例)
| ID | 要件名 | 概要 | 優先度 | 対象画面/機能(ASP側) |
|---|---|---|---|---|
| F-001 | 顧客マスタ統合 | B社顧客をA社顧客マスタへ統合登録 | 必須 | customer_edit.asp 他 |
| F-002 | 受注入力の税区分対応 | 内税/外税を選択可能に改修 | 必須 | order_input.asp |
| F-003 | 旧B社番号での検索対応 | 移行後も旧番号で検索可能に | 推奨 | search.asp |

### 5.2 Classic ASP改修要件(改修方針の明文化)
- **改修方式**:既存ASP資産への追加改修か、部分的に.NET等へリプレースするか
- **影響範囲の特定方法**:共通include(例 `common.inc`)を変更する場合の影響ページ一覧化
- **DBスキーマ変更に伴うSQL文修正箇所の洗い出し**(ADO直書きSQLが多い場合は特に重要)
- **セッション・Cookie仕様の統合方針**(B社ユーザーの認証情報をどう扱うか)
- **文字コード統一方針**
- **改修に伴うセキュリティ是正の要否**(パラメータ化クエリ化など、スコープに入れるか明記)

### 5.3 非機能要件
| 分類 | 要件 |
|---|---|
| 性能 | 統合後のレコード増加を踏まえたレスポンス目標値 |
| 可用性 | 移行時の許容停止時間(メンテナンスウィンドウ) |
| セキュリティ | 認証統合、権限統合後のアクセス制御 |
| 保守性 | 改修後のコード規約、ドキュメント整備方針 |
| 互換性 | 対応ブラウザ(Classic ASPは古いIE依存が残っているケースが多いため要確認) |

## 6. データ移行要件

### 6.1 移行方針
- 移行方式:一括移行(ビッグバン) / 段階移行(並行稼働) のどちらか、選定理由を明記
- 移行タイミング(業務閑散期、締め処理後 等)
- ロールバック方針(失敗時に旧システムへ切り戻せる基準・手順)

### 6.2 データマッピング定義
| 移行元(B社) | 移行元項目 | 移行先(A社) | 移行先項目 | 変換ルール |
|---|---|---|---|---|
| 顧客テーブル | customer_code | 顧客マスタ | CUST_CD | B社コード→A社体系へ変換テーブル参照 |
| 受注テーブル | tax_type | 受注テーブル | TAX_KBN | 外税(1)→内税相当に再計算 |

- 上記を全テーブル・全項目で作成(データディクショナリとして管理)

### 6.3 移行対象・除外基準
- 移行対象データの条件(例:過去3年分の取引データのみ、休眠顧客は除外 等)
- アーカイブ方針(移行しないデータの旧システム側保管・参照方法)

### 6.4 移行方式・ツール
- ETLツール/バッチスクリプトのどちらを使うか
- 移行バッチの実行環境・実行順序(依存関係のあるマスタ→トランザクションの順 等)

### 6.5 データ検証(移行後の整合性確認)
- 件数突合(移行元件数 = 移行先件数)
- サンプリング検証(重要項目の値一致確認)
- 業務担当者によるユーザー受入検証(UAT)の実施方法
- エラーデータの扱い(移行不可データのリスト化・手動対応フロー)

## 8. リスクと対応策

| リスク | 影響度 | 発生確率 | 対応策 |
|---|---|---|---|
| Classic ASPの改修範囲が想定より広い(共通incの影響大) | 高 | 中 | 早期の影響範囲調査、改修前の依存関係マッピング |
| データ移行の想定外エラー(不正データ) | 高 | 中 | 事前データクレンジング、リハーサルでの早期検出 |
| 旧システムの有識者不在(ドキュメント不足) | 中 | 高 | 現行システムのコードリーディング期間を明示的に確保 |

## 補足:Classic ASP × データ移行案件で特に押さえるべきポイント

1. **共通includeファイルの影響範囲調査を最優先で実施する**
   Classic ASPは`<!--#include-->`で共通ロジックを多数のページが参照している構成が多く、1箇所の改修が想定外のページに波及しやすいため。
2. **SQL直書き(ADO)の棚卸しを要件定義段階で行う**
   ORMがないため、テーブル/カラム変更の影響箇所をコードから機械的に洗い出す作業(grep等)を要件定義のタスクとして計画に組み込む。
3. **自動テストが無い前提でテスト要件を厚めに設計する**
   回帰テストの範囲・手順を要件定義書内に明記しておかないと、改修後の品質担保が個人の経験則に依存してしまう。
4. **データ移行はマスタ統合(コード体系統一)が最難関になりやすい**
   顧客コード・商品コードなど、両社で体系が異なる項目の名寄せルールを早期に業務部門と合意する。
